# 发版自动化（release.py）

把台账第四节的发布流程串成命令，**守住"版本必须升、检查必须全绿"的门禁**，不再靠人肉记步骤。

## 三条命令

```powershell
$py = "D:\ServBay\packages\python\current\python.exe"
cd E:\丁厚同\文档\程序\灵枢-skill

# 看现状：本地版本 / 线上 latest / 是否可发
& $py scripts\release.py status

# 1）升版本（X.Y）：自动改四处版本 + CHANGELOG 首节 + 重生成派生文件 + 全套验证
& $py scripts\release.py bump 3.84 "一句话主题"

# 2）发布：校验版本一致+检查全绿 → npm publish → 轮询 registry 到可见
& $py scripts\release.py publish
```

## 各命令细节

- **bump `<X.Y>` `[标题]`**：
  - 拒绝非 X.Y 格式、拒绝新版本 ≤ 当前版本；
  - 改 `SKILL.md` / `package.json`(X.Y.0) / `README.md` / `CHANGELOG.md` 首节；
  - 按依赖序重生成 `sync_engine` → `make_checksums` → `make_manifest`；
  - 跑六项检查 + 行为基线 + 全量测试，**全绿才成功**（任一红即退出码 1）。
  - 不做 git 提交/tag/push。
- **publish `[--wait 分钟]`**：
  - 先跑全套验证；`npm whoami` 确认登录；确认本地版本 > 线上 latest（防 E409 重发）；
  - `npm publish` 后轮询 registry（绕本机 npm 缓存）直到 `latest` == 本地版本——**npm staged 窗口最多 ~17 分钟**，脚本默认等 20 分钟。
- **status**：打印本地/线上版本与"是否可发"。

## 两条铁律（脚本替你守）

1. **新文件必须先 `git add`**：`manifest --check` 会拒绝未入库的发布范围内文件（如新脚本自己）。先 `git add` 新文件再 bump，脚本不替你决定哪些文件入库。
2. **tag/push 不做**：按用户决定，脚本不含 git 提交/tag/push；发版后如需提交，仍按"一个版本一个提交"手工做（提交时排除 `tests/test_*.py` 本地测试文件）。

## 典型发版流程（建议顺序）

```powershell
# 1) 改完功能代码（先别提交版本文件）
# 2) 升版本 + 重生成 + 全套验证（bump 会改 SKILL/package/README/CHANGELOG/manifest）
& $py scripts\release.py bump 3.84 "主题"
# 3) 全绿后，把功能代码 + 版本文件一起提交（一个版本一个提交）
git add -A
git commit -m "feat: v3.84 主题"
# 4) 发布到 npm（等 staged 可见）
& $py scripts\release.py publish
# 5) 同步 DSH 副本 + 重启插件（脚本不做）
powershell -ExecutionPolicy Bypass -File scripts\update_dsh_copy.ps1 -Profile desktop
```

> tag/push 按用户决定不做；提交时排除 `tests/test_*.py` 本地测试文件。
