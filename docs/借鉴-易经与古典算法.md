# 古典算法借鉴：易经八卦体系与其它古籍里的"可计算结构"

> 调研日期：2026-11-24 · 面向灵枢（类脑记忆引擎）
> 目的：把《易经》及同类古籍里**真正是算法的部分**抽出来，评估能不能用在灵枢上。
>
> **先说清立场**：本文只借**结构**（编码、变换、约束、周期、图传播），不借**象征**（卦辞吉凶、占卜、命理）。凡属后者的一律归入「不建议」，并说明为什么——把玄学塞进记忆系统只会制造伪精度和不可解释的评分。

## 一、你给的这段，先补齐它缺的一半

你贴的那段是对的，但只讲了**编码**，没讲**运算**。易经真正的算法价值在后者。

### 1.1 编码（你说的部分，确认 + 补精确）

| 概念 | 位数 | 状态数 | 说明 |
|---|---|---|---|
| 爻（yáo） | 1 bit | 2 | 阳爻 `—`（奇、1、称**九**）／阴爻 `--`（偶、0、称**六**） |
| 八卦（trigram） | 3 bit | 2³ = 8 | 乾☰111 / 兑☱110 / 离☲101 / 震☳100 / 巽☴011 / 坎☵010 / 艮☶001 / 坤☷000 |
| 六十四卦（hexagram） | 6 bit | 2⁶ = 64 | 下卦（内卦）+ 上卦（外卦）叠加 |
| 爻位实例 | — | 64 × 6 = 384 | 每卦 6 个爻位，共 384 个「位」 |

**爻位命名**（你说的规则，举例才清楚）：自下而上为 **初、二、三、四、五、上**；阳爻称九、阴爻称六。
所以乾卦六爻全是阳，从下到上依次是 **初九、九二、九三、九四、九五、上九**；坤卦则是 **初六、六二、六三、六四、六五、上六**。
（顺带一个常被引用的点：「九五」之所以是至尊位，是因为它**既中（第五爻居中位）又当位（阳爻居奇数位）**——这是**约束满足**的结论，不是神秘主义。）

### 1.2 运算（你那段缺的，这才是能借的）

易经有四个**位运算级别的变换算子**，全部可形式化：

| 算子 | 定义 | 位运算等价 |
|---|---|---|
| **错卦**（旁通） | 六爻全部阴阳互换 | `x XOR 0b111111`（按位取反） |
| **综卦**（反卦） | 六爻上下颠倒 | 位序反转 `reverse(x)` |
| **互卦**（互体） | 取第 2·3·4 爻为下卦、第 3·4·5 爻为上卦，合成新卦 | 取中间窗口 `bits[1:4] + bits[2:5]` |
| **之卦**（变卦） | 把某一爻翻转，得新卦 | `x XOR (1 << k)`，k ∈ 0..5 → **每卦 6 个邻居，共 384 条转移边** |

**384 = 64 × 6 的真正含义**：不是"384 种变化"，而是**64 个状态、每个状态 6 条出边的状态转移图**。这是一个**六维超立方体（6-cube）**——每个状态恰好 6 个邻居，直径 6。这个结构在计算机里就叫 hypercube 拓扑，是并行计算里的经典互连网络。

### 1.3 还有两条你没提到但更有用的

- **先天次序 = 二进制计数序**：邵雍的先天六十四卦次序，把卦按 000000→111111 排列，与整数 0–63 一一对应。莱布尼茨看到传教士寄来的卦图后确认这就是二进制——所以「六十四卦 = 6 位二进制计数器」是有明确历史依据的，不是后人附会。
- **爻位关系谓词**（真正的约束系统）：
  - **当位**：阳爻居奇位（1/3/5）、阴爻居偶位（2/4/6）为「当位」，否则「不当位」
  - **得中**：居第 2 或第 5 位
  - **应**：初↔四、二↔五、三↔上，两爻阴阳相反为「有应」
  - **比**：相邻两爻的关系
  这四组谓词构成一套**结构合法性检查**——给定一个 6 位状态，能立刻判出它"合不合理"。这才是最像软件工程的部分。

## 三、逐条评估：哪些真能用，哪些是噪音

### Tier A —— 真能用，建议做（按性价比排序）

#### A1. 六爻位一致性检查 → 「记忆状态格」审计

**思路**：把一条记忆的六个二元特征当作六爻，映射到 64 格，用「当位 / 得中 / 有应」三组谓词判它"合不合理"。

建议的六位定义（自下而上）：

| 爻位 | 特征 | 0 | 1 |
|---|---|---|---|
| 初（1） | 来源 | ai / 派生 | user / 亲历 |
| 二（2） | 审核 | pending | confirmed |
| 三（3） | 层 | dust / archive | hippo / cortex |
| 四（4） | 类型 | 一次性 episode | 稳定 fact / preference |
| 五（5） | 置信 | < 0.6 | ≥ 0.6 |
| 上（6） | 时效 | 已过 review_by | 未过期 / 无期限 |

于是「当位」变成：**阳（1）应居奇位、阴（0）应居偶位**。代入后立刻得到几条**真实的一致性规则**：

- 初位=1（user 亲历）而二位=0（pending）→ **不当位**：用户亲口说的却被挂着待审（这正是 v3.80 修过的 bug，`source=user` 应直接 confirmed）
- 五位=1（高置信）而三位=0（在 dust）→ 结构异常：高置信记忆不该沉在淡忘区
- 二位=1（confirmed）而初位=0（AI 派生）+ 五位=0（低置信）→ **有应性缺失**：AI 派生 + 低置信 + 已确认，是最容易沉淀幻觉的组合

**落地**：`memory shape-audit`（只读），把全库记录映射成 6 位签名，输出 64 格热力表 + 命中「不当位/失应」的记录清单。改动量小（纯只读扫描），收益是**一张能一眼看出数据健康状况的 8×8 矩阵**。
**风险**：低位。位定义要写清楚，否则会变成玄学。

#### A2. 四个变换算子 → 召回鲁棒性（`recall --robust`）

| 算子 | 文本层的等价操作 | 检验什么 |
|---|---|---|
| **错卦** | 取反：`X` ↔ `不X`、`要` ↔ `别` | **否定敏感性**：灵枢已有 `remember --avoid` 负空间，但召回时**没区分"要做"和"别做"**——错卦正是这个算子的形式化 |

**关于"否定不敏感"，我实测过（2026-11-24，隔离库三条记忆）：**

```
库内：①「不要用 DiskGenius 恢复分区，会破坏分区表」(avoid)
      ②「用 DiskGenius 做分区备份是可行的做法」
      ③「分区恢复推荐先做只读镜像再动手」

recall "用 DiskGenius 恢复分区"      → ①, ②, ③   ← 注意：第一条是「不要用」
recall "不要用 DiskGenius 恢复分区"  → ①, ③, ②
```

**结果集 3/3 完全重合**，只有排序不同。所以准确的说法是：

- 召回**不是完全不敏感**（顺序确实变了），但**结果集不区分语义方向**；
- 真正的毛病更具体：**肯定查询把「不要用」的禁止记忆排到了第一位，且结果里没有任何标记说明它是禁止项**——模型看到这个，很可能按"要用"去理解。

这正是「错卦」算子要解决的事：把查询与其取反一起做，然后**按语义方向过滤/标注**，而不是只依赖词面重合。

**✅ 已实现（v5.1）**：`recall` 现在会算「查询极性」与「记忆极性」，
**方向相反时打标 `polarity_conflict`**，CLI 输出 `⚠ 这条是禁止/否定方向（avoid），与你的查询方向相反——别读反`。

设计上刻意**不静默降权**：把禁令藏起来比标出来更危险——模型可能因此真的去做那件被禁止的事。
所以做法是"保留 + 显式标注"，把判断权交回给模型/用户。

注：注入路径本来就已经按"已经排除的方向（别再提）"独立成块，不存在这个歧义；
缺口只在 `recall` 的检索输出。
| **综卦** | 词序反转 | **语序鲁棒性**：中文二元组本就无序，反转后结果应几乎不变；若变化大，说明打分对语序敏感（是个 bug） |
| **互卦** | 取中间窗口为核心 | **核心提取**：长记忆的"核"在中段（首尾多是铺垫/尾巴），与现有 `gist` 互补 |
| **之卦** | 6 个单 bit 扰动 | **稳定性**：翻转一个关键词，Top-K 不应剧烈变化；变化大 = 召回不稳 |

**落地**：`recall --robust` 跑原查询 + 上述扰动，输出「原 Top-K 与扰动后 Top-K 的重合率」。这是**可度量的质量指标**，不是感觉。
**风险**：低。全部只读，且不改变默认行为。
**特别值得做的是「错卦」**——它是唯一能解决实际缺陷的：现在 `recall "不要用 DiskGenius"` 和 `recall "用 DiskGenius"` 会拿到同一批记忆。

#### A3. 盈不足术 → 标定 `charsPerToken`

灵枢的水位估算一直用固定常数 `charsPerToken = 2`（`cordis-plugin/lingshu-cron/plugin.js`），中文语境下这是粗估。而宿主其实偶尔会给**真实 token 数**。

**盈不足（双假设法）**就是：拿两次观测 `(chars₁, realTokens₁)`、`(chars₂, realTokens₂)`，解一次线性方程反推真实系数，并据此修正后续估算。
**落地**：把每次"宿主给了真值"的样本记进 `~/.brain-memory/token-calib.jsonl`，用最小二乘拟合 `charsPerToken`，水位估算读拟合值（样本不足时退回 2.0）。
**风险**：低。纯增量，且天然 fail-open。

#### A4. 六十甲子 → 双周期复习调度

现在记忆复习用的是**单一时间衰减**（`retention` / 半衰期）。六十甲子的启发是：**两个独立周期叠加，用 LCM 判断相位重合**。

**落地**：复习优先级 = `f(距上次复习的时间周期, 被召回次数周期)`，两个周期分别以不同粒度推进（如 7 天 × 5 次），当两者同时"归零"时给一次强化复习。好处是**避免所有记忆在同一节律上被同时唤醒**（现在 `due_for_review` 就是齐步走的）。
**风险**：中低。要防过度设计——先用一个可解释的简单版本。

### Tier B —— 有道理但收益不确定，暂不做

| 项 | 想法 | 为什么暂缓 |
|---|---|---|
| **五行生克 → 带符号关联图** | 把 `assoc.jsonl` 的边分成「生」（支持/延伸）与「克」（矛盾/抑制）两类，传播时带符号 | 方向是对的（记忆确实有"互相支持"和"互相矛盾"两种关系），但灵枢现在的 `assoc.jsonl` **基本是空的**（实测真实库里没有这个文件），先要有图才谈得上传播 |
| **九宫 → 固定槽位轮转** | 用 3×3 幻方做均匀淘汰/轮转，保证覆盖均匀 | 现有 LRU/分层保留已经够用，收益边际 |
| **二十四节气 → 维护档位** | 把定时任务切成 24 档而非"时/天/周" | 现在的 6h/日/周三层已经覆盖，24 档属于过度细分 |
| **十二律 → 等比保留序列** | 备份保留份数按 3/2 比率链生成（如 4→6→9→13…） | 现有的 6/7/4 分层简单可预期，换成比率链反而难解释 |
| **六书 → 复合记忆构造法** | 用"形声"（语义部首 + 语音）类比"标签 + 实体"的复合键 | 概念有趣，但灵枢的 tag/entity 已经够用，没有明确缺口 |

### Tier C —— 明确不建议

- **卦辞/爻辞文本、吉凶判断、占卜**：没有算法内容，纯解释系统。
- **用卦象给记忆打"命运标签"**：会制造伪精度，且**破坏可解释性**——灵枢的全部评分（relevance/recency/importance/core_bias/primacy）都能追溯到具体数值，一旦混入卦象就说不清了。
- **河图洛书的"数理玄机"式解读**：3×3 幻方就是个幻方，没有更多。
- **把 384 当成"覆盖全部可能性"**：6 位只能区分 64 种状态，说"代表现实事物发展的全部可能路径"是修辞，不是事实——64 格远不足以描述记忆空间，别被这个数字带偏。

## 五、一句话总结

易经值得借的是**它作为一套 6 位编码系统的工程性**：

- **64 格状态空间 + 6 条出边的超立方体**（结构）
- **错/综/互/之 四个位变换算子**（算子）
- **当位/得中/有应 三组结构谓词**（约束）

而**不该借**的是它的解释层（卦辞、吉凶、占卜）。把前三个用起来，灵枢能得到一张**状态审计矩阵**和一套**召回鲁棒性度量**；把后一个用起来，只会得到一堆说不清理由的分数。

## 六、实测结论：字面谓词不能直接搬（重要修正）

前面把「当位 / 得中 / 有应」列为可借的"结构谓词"。**实现后在真实库上跑出来，它们几乎不区分**：

| 谓词 | 真库 306 条的违规率 | 判断 |
|---|---|---|
| 当位（阳居奇位/阴居偶位） | **100%** | 无区分度——每条都违规，等于没说 |
| 失应（三对对应爻全同） | 74% | 接近基线，无信息量 |
| 未得中（二、五爻皆阴） | 75% | 同上 |

**原因**：这六位特征（来源/审核/层/类型/置信/时效）并不是为"交替排列"设计的。硬套字面规则 → 每条记录都判一次违规 → 正是我在第三节警告过的**伪精度**。

**修正做法（已实现）**：保留真正有用的部分——**64 格状态分布**（真库落在 14/64 格，其中一格占 221 条，说明数据高度集中）——把约束换成三条**有领域含义的不变量**：

| 不变量 | 含义 | 真库命中 |
|---|---|---|
| ① AI 派生 + 已确认 + 低置信 | 最易沉淀幻觉的组合 | **13 条（4%）** |
| ② 高置信却在淡忘/归档层 | 可能被误淡忘（可 `memory boost`） | **4 条（1%）** |
| ③ 稳定事实已过 `review_by` 未复核 | 该进 `review-list` | 0 条 |

命令：`brain.py memory shape-audit [--json] [--limit N]`（**纯只读**）

**这才是这次调研最有价值的一条结论**：易经给的是**编码与变换**（64 格、错/综/互/之），不是**判据**。判据必须从领域里来。

## 七、底层保险：业界怎么做的（附借鉴来源）

你要求"加一个底层保险"，这是本次真正落地的东西。核心问题是：`save_all()` 是全项目最高危的写入口（17 个公开函数最终都落到它），一旦读写之间丢记录或层名写错，**整层被覆盖**。

| 出处 | 借的东西 | 本项目如何落地 |
|---|---|---|
| **ARIES**（Mohan et al., 1992） | 写前记 undo 日志，出错按日志回滚 | 写前快照 = undo log |
| **rsnapshot / Time Machine 本地快照** | **硬链接即快照**：`os.link()` 是 O(1)、零拷贝，天然 COW | `safety_net.snapshot()` 用 `os.link()`，跨卷才退回复制 |
| **crash-only software**（Candea & Fox, 2003） | 假定随时会崩，恢复逻辑放在常路 | 每次写后都校验，不依赖"优雅关闭" |
| **SQLite WAL / LMDB COW B+tree** | 单写者 + 原子替换 + 校验 | 项目本来就用 `temp + os.replace`，正好支撑硬链接快照 |
| **shadow paging**（早期数据库） | 写新页、切指针，不覆盖旧页 | 同上 |
| **blue-green / 金丝雀** | 新版本先影子跑，验证再切 | 灵枢的水位自动化已有 shadow 模式，后续新功能沿用 |

### 关键发现：硬链接快照**只在原子替换下成立**

实现时踩到一个真坑：如果某处代码**就地截断写**（`open("w")`），它改的是**共享 inode**，快照会跟着一起被改坏——快照形同虚设。

所以最终设计加了一层：**快照时记 sha256，回滚前先验指纹**。指纹不符就**拒绝回滚**并报错（拿脏快照覆盖比不回滚更糟）。

### 交付内容

- `scripts/safety_net.py`：`snapshot()` / `verify()` / `restore()` / `list_snapshots()` / `guarded_write()`
- 接进 `memory.save_all()`：**写前快照 → 写后校验 → 失败自动回滚**
- 校验内容：JSON 每行可解析、末行完整、**层级自洽**（记录自带 `layer` 必须与所在文件匹配）
- 配置：`safety_snapshots` / `safety_verify` / `safety_keep`（默认 20 份；更旧的移入 `.safety/.pruned/`，**不删除**）
- fail-open：快照或校验自身出错**绝不阻断主写入**

### 已验证（6/6）

快照是硬链接、层级错位能被抓、截断能被抓、坏写能自动回滚（哈希级一致）、**污染的快照会被拒绝回滚**、超份数移入 `.pruned/` 而非删除。

### 只读性证明

在**真实记忆库**上跑 `memory shape-audit` + `memory integrity` 前后，9 个数据文件 sha256 **一字未变**。
