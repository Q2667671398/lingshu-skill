### P2d · 中途重复注入与缓存前缀（2026-11-21 用户报障后新增）

> 用户原话：「每次对话上下文注入完，在对话还会注入，上下文没有压缩但是灵枢还会注入上下文」。
> 代码实证（`cordis-plugin/lingshu-cron/plugin.js`、`lingshu-startup/plugin.js`）找到**四个**独立成因，
> 其中两个直接违反业界的提示词缓存前缀原则——不是"多花点 token"，是**让缓存大面积失效**。

**成因一：软自检每 10 轮固定注入一次**（[plugin.js:947-959](../cordis-plugin/lingshu-cron/plugin.js#L947-L959)）
```js
const every = Math.max(0, Number(cfg.waterCheckTurns) || 0)   // 默认 10
if (every > 0 && step === 0 && n > 0 && n % every === 0 && st.softAt !== n) { ...notice(...) }
```
不管水位多低（实测注入过 14%）、不管模型是否真需要，每 10 轮就塞一条 `【灵枢·水位自检】`，而且文案还**叫模型再跑一次 `check-context`**——等于多一次工具往返。这正是用户看到的"没压缩却还在注入"。

**成因二：`pruneInjected` 会从历史里删消息**（[plugin.js](../cordis-plugin/lingshu-cron/plugin.js) 的 `pruneInjected`，默认 `true`）
它按 `m?.source?.name !== 'lingshu'` 过滤掉旧注入消息。但 OpenAI 的提示词缓存是**从请求开头逐项匹配**的，删掉历史中段的消息等于**改写前缀**——从该处往后全部无法复用缓存，新模型还会丢弃变更点之后的推理项。原文：[保持前缀不变](https://developers.openai.com/zh-Hans/api/docs/guides/keep-prefix-unchanged)。"删掉省 token"在这里是**净亏**。

**成因三：两个子插件共用 `source.name === 'lingshu'`**
startup 注入的记忆块与 cron 的瞬态提醒**同名**，于是 cron 的 prune 会把 startup 注入的记忆块一起删掉（谁先跑谁赢）。结果是记忆块可能被抹掉、或被反复补回。

**成因四：`resume` 无条件再注入一整份**
`agent/created` 对 `source === 'resume'` 也注入（`cfg.injectResume` 默认 `true`），而会话历史里**已经有一份**同样的记忆块 → 同一个对话里出现两份 1214 tokens，正是"没有压缩却又注入一遍"。

**业界做法（已查证，可借鉴）**

| 来源 | 观点 | 对灵枢的含义 |
|---|---|---|
| [OpenAI·保持前缀不变](https://developers.openai.com/zh-Hans/api/docs/guides/keep-prefix-unchanged) | 缓存从开头逐项匹配；改历史＝改前缀＝后续全部失效；应**只在末尾追加** | `pruneInjected` 默认值应当反过来（默认不删） |
| [Cache-Preserving Injection（agent-memory-atlas）](https://github.com/neoneye/agent-memory-atlas/blob/0e8db5c6b45c16fa4c6e1decf3696105999760c5/docs/patterns/cache-preserving-injection/index.html) | Nuum 按"epoch"冻结记忆段，让 system prompt 逐字节不变、只在压缩时更新；Reasonix 按位置分流：稳定段进缓存前缀，事实走用户文本之后的 recall 块 | 记忆块应"一会话一冻结"，会话中不再重复注入 |
| [pydantic-ai·System Reminders](https://github.com/pydantic/pydantic-ai/blob/e2fbcf609852600e2f2e2eabb18c0b233c49a937/docs/harness/system-reminders.md) | 提醒按条件注入（如 `run_step > 20` 才提"该收尾了"），静态/动态分层 | 水位自检应改条件触发，而不是固定周期 |
| [koi·goal-reminder](https://github.com/windoliver/koi/blob/207268ceda92a626ac7931eec6b30eecdfef4603/docs/L2/middleware-goal-reminder.md) | 有漂移检测：连续 3 条消息命中关键词即 on-track → **间隔翻倍**；漂移才重置为基础间隔 | 灵枢可照抄"不漂移就降频"的思路 |
| [State-Control Architecture](https://zenodo.org/records/21435275/files/State-Control%20Architecture%20Tech%20Report.pdf?download=1) | 按重要性决定注入频率（critical 每轮 / low 仅 1 轮） | 水位提醒属 low，不该高频 |

**评估过但不做的**（写下来免得再问）：

    - **Letta / MemGPT 四层**（[架构综述](https://raw.githubusercontent.com/MohamedAbdallah-14/prompt-to-asset/refs/heads/main/docs/research/30-agent-memory-state/30a-agent-memory-architectures.md)）：message buffer（原始对话 FIFO）+ core memory（常驻人格，agent 可编辑）+ recall memory（可搜索历史）+ archival memory（长期向量/图）。灵枢已有 hippo/cortex/dust/archive 四层，但 **core memory 的"agent 可编辑"语义**没有——人格只能靠 `persona` 命令改，模型不能自主更新常驻块。借鉴方向：给模型一个受控的 core-memory 编辑入口（带白名单字段），像 Letta 的 core memory block。
    - **dual-mem L0–L7 八层**（[dual-mem](https://pypi.org/project/dual-mem/0.1.2/)）：L1 完整对话原文、L2 事实、L6 行为模式、**L7 意图/未来计划**（"准备跑马拉松"）。灵枢有事实/习惯/人格，但**没有独立的"意图/待办"层**——`work` 是会话暂存（12h 丢）， dreams 的"未完成事"是临时摘要。借鉴方向：加长期意图层（用户说明的目标/计划，带 TTL 和完成标记），跨会话保留。
    - **foldkeep**（[foldkeep](https://pypi.org/project/foldkeep/0.9.2/)）：零依赖、确定性上下文压缩，**pinned fact layer 保住每个决策可达 + lossless base 可逐字展开任意旧轮次**。灵枢的做梦是 LLM 提炼（有损、不可展开）。借鉴方向：给 capture 的 verbatim 归档加"逐字展开"入口（`recall --verbatim <id>` 读原文），让压缩后的记忆可逆。注：capture 已存 verbatim 全文到 `verbatim/*.md`，只是没有按 id 关联的召回入口。
    - **SocialMemBench**（[arXiv](https://export.arxiv.org/pdf/2605.17789)）：群聊记忆要"correctly attribute"说话人、区分群体规范与个人例外。灵枢的通道记忆有三元组隔离，但**没有群体规范 vs 个人例外的区分**。借鉴方向：`channel` 层加"群规"类型（默认继承、个人可覆盖）。
    - **阿里云表格存储 Memory 最佳实践**（[docs](https://help.aliyun.com/en/tablestore/table-store-service/memory-storage-recommendations#1)）：stable Scope（appId/tenantId/agentId/runId 四字段）+ 同步/异步写分离。灵枢的 scope 只有 channel/group/user，缺 agentId/runId——多 agent 同库时可能串。借鉴方向：评估是否需要加 agent 维度（低优先）。

71. **【已修 v4.1】`test_checkpoint.py::test_cli_json_roundtrip` 全套里偶发失败**：单跑稳定（压测 10/10），按全套顺序连跑也难复现——**根因不是测试，是生产代码把瞬时故障说成了业务结论**：
    - `checkpoint._git()` 原来是 `except Exception: return ""`，把**瞬时占用（杀软/索引器 WinError 5/32/33/145）、20s 超时**和"这不是 git 仓库"混成一个空串；

    - 测试断言 `assert data["ok"]` 没带消息 → flake 时只有空 AssertionError，排查无门（`io_retry_util` 按设计**不重试 AssertionError**，所以重试也救不了）。

    **副产品**：`OSError(32)` 的 `errno` 也纳入瞬时判定（Windows 原生错误才带 `winerror`，纯 OSError 没有）——首版修复漏了这点，靠回归测试抓出来。

### 发版顺序（照这个走，别跳步）

派生文件是**生成物**，必须先生成、再检查。顺序错了会出现"改一个文件红五项"的假失败：

1. **改完源码/文档后先生成**（三者有依赖，按此序）：

4. 提交（一个版本一个提交；v3.46/v3.47 的教训是别再混写两个主题）。
5. 打 tag `vX.Y`——**必须打在本版发布提交上**，不能打在后面的文档补遗提交上（`check_tag.py` 自 v3.50 起允许 tag 是 HEAD 祖先，但会核对 tag 是否确实标在本版上）。

#### 七、这次踩出来的四条纪律

1. **PowerShell 5.1 的脚本必须带 UTF-8 BOM**。中文注释在无 BOM 时被按 GBK 解析，直接语法错误（`Unexpected token 'files'`）。任何给 PowerShell 5.1 跑的 `.ps1` 都要 BOM。
2. **改已安装插件的代码不会自动生效**。首次安装走热更新，改文件不重载；必须把插件关一次再开一次才装载新模块，否则会对着旧规则排错。
3. **规则宁窄勿宽**。第一版把 `Set-Content` 当"覆盖风险"，结果连正常写文件都被拦。破坏性判定必须区分"写"和"覆盖已有文件"，没有可靠判据时就不该拦。
4. **拦截是防误操作，不是安全沙箱**。它拦不住脚本、变量、程序内部的间接修改——文档里必须如实这么写，不能给虚假的安全感。

#### 十三、记忆审核：规则闸 + 待审摘要（已定方案）

**问题**：自动写入的记忆没人复核（自动写 = 会话结束时模型已不在场），而全文审核很贵。

### 实测成本

| 项 | 实测 |
|---|---|
| 当前 startup 注入包 | 1283 字符 ≈ **640 tokens**（预算 1400） |
| 其中人格段 | 432 字符 = 216 tokens（约 2 字符/token） |
| 待审块塞全文（10 条 × 150 字） | +1500 字符 ≈ **+750 tokens**，注入预算几乎翻倍 |
| 待审块只给 id + 40 字要点 | +400 字符 ≈ **+200 tokens** |

### 方案：A + B 组合

**A. 写入前规则闸（0 token）**

在 `remember` / `work flush` / `daily` 的写入口做确定性校验：空内容、与近 7 天高度重复、含密钥特征、超长（>1200 字）、没有主语要素 → 直接标 `pending` 或拒绝写入。判断全在本地，不调用模型。

**B. 待审摘要注入（约 200 token，且只在有 pending 时出现）**

- 注入块**只给 `id` + 40 字要点 + 来源**，全文用 `recall <id>` 按需取；
- 下一会话开头看到清单，用 `review confirm` / `review discard` 处理；
- `review` 输出每行追加一句"建议动作"（保留/丢弃/合并），减少模型二次判断。

**C. 全文自审只在 75% 水位做梦时做**——那时本来就要压缩上下文，不额外付费。
**D. 本地小模型审核**（Ollama 0.6B）作为可选，不引入依赖。

### 落地清单

1. `pending_memory_reviews()` 增加 `--brief` 输出，注入层默认只取摘要；
2. `work flush` / `daily` 的产出默认 `review="pending"`；
3. `review` 每条加"建议动作"一行；
4. 文档写明：**审核窗口在下一会话开头，不在会话结束后**。

#### 十四、灵枢内部的删除护栏（已确认方向，方案已按实测修正）

> 方向确认：**灵枢内部为主，同时保留 DSH shell 插件**（两层都留）。

### 实测修正：灵枢其实已经删得比想象中谨慎

| 命令 | 真实行为 | 确认 | 备份/反悔 |
|---|---|---|---|
| `forget <id>` | **已是软删除**：移入 dust 淡忘层，记录仍在 | 无需（可逆） | ✅ `revive` / `fold` / `unfold` 可捞回 |
| `memory purge <id>` | 物理删除，但已有**两道闸**：必须在 dust 层且 `forgotten_at` ≥ 7 天 + `--confirm` 手输 id 前 8 位 | ✅ 已有 | ❌ **无备份，删了就是删了** |
| `restore --exact` | 清受管文件 | ✅ 非交互必须 `--yes` | ✅ 恢复前自动备份 |
| `backup --keep` 修剪 | 直接 `unlink` 旧备份 zip | ❌ 无 | ❌ **无留档** |

**结论：真正缺的只有两处**——`purge` 物理删除前没有留底，`backup --keep` 修剪直接 unlink。
`forget` 已经是"可反悔"的形态（dust + revive），不需要再造一个 `trash/` 目录。

### 修正后的方案（更小、更准）

1. **`purge` 留底（软删除台账）**
   物理删除前，把完整记录追加进 `<记忆库>/trash.jsonl`（含 `deleted_at`、原始层、来源）。真删之后仍可从台账恢复；
   `trash restore <id>` 回写；`trash list` 查看；台账超过 90 天由 `daily` 清理。
   代价：一条记录几十到几百字节，比整库备份便宜得多。

2. **`backup --keep` 修剪改为"移走"**
   不再 `unlink`，改移到 `<备份目录>/.pruned/`，保留 7 天再清。这样"备份策略误配把好备份删光"也能救。

3. **统一确认入口（可选，第二步再做）**
   新增 `safety.confirm_destructive()`：TTY 下问一句并列出影响面，非 TTY 必须 `--yes`。
   目前 `restore` 自己写了一份确认逻辑，`purge` 用 confirm token——两套并存可以工作，统一是锦上添花，不是刚需。

### 执行顺序（按用户答复）

**备份 → 问 → 执行；用户拒绝时，把刚做的那份备份删掉。**

理由：先备份才能在"问"的时候把备份路径一起给用户看；拒绝就清理，不留下无用备份垃圾。
（注意：清理的必须是**本次新建**的那份，不能碰历史备份。）

### 四、运维与使用体验

- **面板无常驻方案**：`brain.py serve` 随终端/会话结束而死，没有服务化（Windows 服务/计划任务）的官方做法。
- **备份成功没有"跨卷"确认**：`pick_backup_dir()` 会静默挑一块别的盘，但不会在输出里明确说"本次备份跨卷，可抵御整盘丢失"。
- **memory 审核闭环没接上**：`pending` 标记存在、`review` 命令存在，但自动写入（`work flush` / `daily`）产出的记忆是否标 pending 未确认——这直接关系到第十三节的方案能否落地。

### 五、建议优先级

1. **先改默认值**：`lingshu-guard` 的 `shadow` 默认改 false（或首次启动强制提示一次），这是唯一"以为有防护其实没有"的问题。
2. **补 XSS 转义**：面板是唯一能渲染记忆原文的地方，成本低、风险实在。
3. **修锁泄漏**：一行清理逻辑，长跑进程迟早踩到。
4. **审核闭环**：按第十三节落地（规则闸 + 摘要待审）。
5. **工程债**：覆盖率 → 性能基线 → 副本合并，按季度推进，不要一次性动。

#### 十九、会话互通信箱：用灵枢扩展（ext）实现多会话协作

> 提出日期：2026-11-21。状态：**方案已调研并经用户确认，待实现**（2026-11-21 更新：用户已选"更新第十九节方案状态"，按确认推进；实现仍按第十五节流程在确认后执行，本节尚不含已写的代码）。
> 排期说明：本节是 2026-11-21 新提的方案，顺延编号置于第十七节"落地情况"快照之后；编号按提出时间排。
> 需求原文：让 DSH 的多个会话之间能**互相通信、互相操控**，并跟灵枢记忆体系打通，做成"灵枢的工具"。

### 一、先厘清需求与边界

这句话拆开是三件不同的事，市面上没有单一工具全包，但三层各有着落：

| 层 | 需求 | 现成参照 | 灵枢里怎么落 |
|---|---|---|---|
| A 互相操控 | 一个会话让另一个会话干活、推进回合、拿回结果 | `dsh-mcp-btwy` / `@liuxinye/dsh-ai-chat-mcp`（把 DSH 开放成 MCP 服务端），实测 npm registry 确认存在（v1.2.4 / v0.1.0） | 属 DSH 插件层，**不写进灵枢扩展**；本节只登记为外部依赖，不重复造 |
| B 互相通信 | 常驻会话之间递消息、收件箱、回执 | AMQ（Maildir 原子投递 `tmp→new→cur`）、spanreed / clatter-bus（会话间总线 + `crossSessionInbound` 审批门） | **本节重点：用 ext 写一个信箱扩展**，见下文 |
| C 灵枢打通 | 消息沉淀成记忆、按会话身份隔离 | 灵枢已有的 `(channel, group_id, user)` 三元组 + `session` 字段 | 消息回写走 `remember --kind relationship/episode`，身份复用三元组 |

**协议分工**（别混）：MCP = agent→工具/数据（A 层），A2A = agent↔agent（B 层的标准化方向）。本地多会话场景，ext 信箱比引 A2A 栈轻得多。

### 二、为什么用 ext，而不用插件 / 外部总线

1. **ext 是灵枢原生挂载点**：`~/.brain-memory/extensions/*.py` 的 `inject(ctx)` 并入每会话注入、`run(argv)` 加自定义命令，**更新技能永不覆盖**——正好符合"灵枢的工具"定位（`growth.py:3576-3577`）。
2. **坏模块隔离**：单个扩展抛异常被静默跳过，不影响灵枢本体（`growth.py:3664-3673`）。
3. **安全默认关**：扩展是任意 Python 代码，`extensions_enabled` 缺省 `false`，需显式开启（`growth.py:3649-3663`）。这是刻意的——信箱扩展能读上下文，必须先获信任。
4. **外部总线太重**：AMQ 要 Go 二进制、spanreed/clatter 偏 Claude Code + tmux + Linux；本机是 Windows + DSH，引它们收益低于成本。借鉴思路（Maildir、审批门）即可，不引依赖。

### 三、实测约束（决定设计，不是猜）

读 `E:\丁厚同\文档\程序\灵枢-skill` 真身代码确认：

- `inject(ctx)` 的 ctx **只有 `{"query":..., "mode":...}`**（`memory.py:4350`）——**拿不到当前会话 ID**。所以"这条消息发给谁/我是谁"不能靠 ctx 自动识别，必须显式解决（见下）。
- `inject()` 返回文本被截断到 **800 字**（`growth.py:3671`）——收件箱注入只放"未读数 + 最近几条摘要"，全文按需 `bus read` 取。
- `run(argv)` 由 `brain.py ext run <名字> [参数]` 调用，参数整个列表传入（`growth.py:3705-3707` 模板）。
- 会话身份可用现成字段：记忆记录带 `channel` / `group_id` / `user`（`memory.py:958,967`）和 `session`（缺省 `default`）。

### 四、方案设计：`session-bus` 扩展

**落盘位置**：`~/.brain-memory/session-bus/`（数据目录内，随备份走；下划线开头文件忽略）

```
session-bus/
  inbox/
    <会话ID>/            # 每个会话一个 Maildir 信箱
      new/<ts>-<from>-<seq>.json   # 未读：原子 rename 投递
      cur/<ts>-<from>-<seq>.json   # 已读：读后从 new 移到 cur
  outbox/
    <ts>-<to>-<seq>.json # 投递日志（审计 + 回执）
  profile.json           # 本机会话注册表：会话ID → 别名/通道身份
```

**消息格式**（JSON，UTF-8）：

```json
{
  "id": "m_<ts>_<rand>",
  "from": "<会话ID或别名>",
  "to": "<会话ID或别名>",
  "ts": 1795...,
  "kind": "task|reply|notice",
  "body": "正文（≤2000 字）",
  "reply_to": "<可选，回执链>",
  "status": "delivered|read|done"
}
```

**四个命令**（`ext run session-bus ...`）：

| 命令 | 作用 | 实现要点 |
|---|---|---|
| `bus send <to> <kind> <body>` | 投递消息 | 写 `tmp/` → 原子 `rename` 到目标 `new/`（Maildir 语义，crash-safe）；同时记 outbox |
| `bus inbox [--session <id>]` | 列本会话未读 | 扫 `inbox/<自会话>/new/`；`--session` 缺省时从注册表或环境变量推断，推断不出则报错要求显式给 |
| `bus read <msg-id>` | 读全文并标已读 | `new/` → `cur/` 原子移动；正文可 `remember` 沉淀 |
| `bus reply <msg-id> <body>` | 回执 | 取原消息 `from` 作 `to`，带 `reply_to` 链 |

**inject 行为**：每会话注入一行——

```
[会话信箱] 未读 N 条（来自 A、B）；用 `brain.py ext run session-bus inbox` 查看
```

N=0 时不注入（不浪费预算）；有未读时最多列 3 个来源，全文不进注入。

**会话身份怎么解决**（ctx 拿不到 ID 的对策，三选一）：

1. **显式别名**（推荐起步）：`bus register <别名>` 把当前工作区路径映射到别名，消息用别名寻址；调用方在会话里手动 `register` 一次。
2. **通道身份**：复用三元组 `(channel, group_id, user)`，IM 会话天然有；本机 CLI 用 `session` 字段。
3. **环境变量**：宿主启动时注入 `LINGSHU_SESSION_ID`，扩展读它——需要 DSH 侧配合，暂不做。

**与灵枢打通**：`bus read` 时按 `--remember` 把正文写成 `relationship`（谁找过我）或 `episode`（协作事件）记忆， Importance 6-7；消息里的承诺/截止 → `fact` + `importance 8`。这样"别的会话说过什么"进长期记忆，下次 startup 自然带出来。

### 五、鉴权与安全（不能省）

你实测过 owner/admin 白名单是空的（`brain.py channel owner list` 全空；`/testauth` 那次确认空名单 = 通道身份谁都过不了）。信箱扩展必须**自己带闸**，否则等于把会话控制权向所有入口敞开：

- **发送鉴权**：`bus send` 在通道上下文（带 `--user`）时校验 owner/admin 白名单；纯本机 CLI（无 `--user`）放行（与 `_require_privileged` 口径一致，`cli.py:1262-1294`）。
- **读取隔离**：每个会话只能读自己的 `inbox/<自会话>/`；跨会话读需 owner 权限或显式授权。
- **审批门借鉴 spanreed**：不同权限模式的会话之间传消息（一方需审批、一方免审批）默认扣留并提示，超时丢弃——避免"免审批会话"绕过对方的安全策略。
- **泄漏面**：inject 只给未读数与来源别名，不给全文；`body` 上限 2000 字；扩展文件路径校验拒绝 `..` 穿越（复用 `_ext_path` 的守卫，`growth.py:3589-3591`）。

### 六、落地清单（按第十五节流程，确认后执行）

1. 新建扩展 `~/.brain-memory/extensions/session-bus.py`（用 `brain.py ext new session-bus` 起手，再 `ext edit` 填正文）。
2. `ext check session-bus` 语法自检 → `config set extensions_enabled true`（**需用户明确同意**，等同允许本机运行扩展代码）。
3. 实现 `send` / `inbox` / `read` / `reply` / `register`，Maildir 原子投递，消息上限与身份守卫。
4. 实现 `inject`：未读摘要行，N=0 不注入。
5. 打通 `remember` 沉淀（可选第二步）。
6. 验证：两个会话互发 → `inbox` 见未读 → `read` 标已读 → 全文 `recall` 能取；`doctor` 不因扩展变红；扩展抛异常时灵枢照常工作。
7. 文档：SKILL.md 扩展章节补一行 `session-bus` 用法（若决定长期保留）；活台账登记版本与验证方式。

### 七、风险与取舍（理智过闸）

- **收益**：多会话能分工协作、结果回传，且消息进灵枢长期记忆——这正是"跨会话"诉求的原生解法。
- **成本**：写一个约 150-250 行的 Python 扩展 + 一轮双会话实测；启用扩展带来任意代码执行面（必须用户确认）。
- **不做的**：不引 AMQ/spanreed 二进制，不写 A2A 协议栈，不改灵枢核心——全部收敛在一个可被"更新永不覆盖"的扩展文件里，可随时 `ext rm session-bus` 回滚。
- **与 A 层的关系**：本扩展解决"通信/消息"，不解决"操控别的会话执行任务"；后者交给 `dsh-mcp-btwy` 插件（A 层）。两者互补，别指望一个扩展既当信箱又当遥控器。
