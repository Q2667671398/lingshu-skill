## 一、现在就是坏的（先修这两条）

### 1. CI 从 1c6d91e 起必然全红 ★

**证据**
- `.gitignore` 第 53 行有 `tests/`，`git ls-files tests` 返回 **0** 个文件；
- `.github/workflows/ci.yml` 却仍然跑 `python tests/test_privacy_scope.py`、`test_plugin_smoke.py`、`test_v302_batch1.py`、`test_v302_batch2.py`，最后还有 `compileall -q scripts tests`；
- 移除发生在 `1c6d91e chore: tests/ 移出仓库本地化（测试脚本永远不推送）`（删掉 1297 行测试，只加了 6 行 .gitignore），之后 `0f78325 / 4f48e5b / 7e51fb0 / 91c1e24` 四次推送都会让 Actions 报红。

**后果**：CI 红着红着就没人看了——等于没有 CI，而下一次真出问题时也分辨不出来。

**做法**（三选一）
1. 测试放回仓库：它们纯标准库、不含密钥，唯一"本地化"的理由是体积，但 1300 行不值得换一个坏掉的 CI；
2. 测试放独立私有仓库，CI 里 `git clone` 后跑；
3. 承认不做测试：删掉那几个 step，CI 只保留一致性检查（check_version / manifest / sync / checksums），别留假的绿色承诺。

**顺带**：`.gitignore` 里 `tests/` 写了两遍（重复行），顺手删一行。

### 2. AstrBot 的 engine 副本已经漂了

**证据**：`python scripts/sync_engine.py --check` → 退出码 1，报 `memory.py`、`persona.py` 与 `engine/` 不一致。

**后果**：AstrBot 宿主跑的是旧引擎——同一个记忆库，两个宿主行为不同；这正是 v2.83 A3 那条"副本漂移"的复发。

**做法**：跑一次 `sync_engine.py` 修平；然后把这条检查并进 `doctor`（现在九项里没有 engine 一致性，只有 SKILL/package 的版本矩阵）。

## 二、结构性漏接线

### 3. `project` 隔离设计了但没接上 ★

**证据**
- `memory.remember(..., project=...)` 有参数，但 `cli.py` **没有** `--project`，`cordis-plugin/*/plugin.js` 里也搜不到 project；
- 实际数据 42 条：project 空 **21 条**、`default` **19 条**、`proj-A/B` 各 1 条（测试残留）。

**后果**：召回完全不看 project（只有 supersede 比较时用），多项目共库时技术细节互相污染；"同源才比较"退化成"全同源"，冲突检测噪声变大。

**做法**
- CLI 加 `--project`，缺省取 `LINGSHU_PROJECT` 环境变量，再缺省取 cwd 目录名；
- DSH/其他宿主插件 spawn 时把 workspace 名传进去；
- `recall` 默认同项目优先（跨项目降权而不是排除），`inject` 同理；
- 老数据（空）按 `default` 处理，不迁移。

### 4. importance 通胀，分档已失去区分度

**证据**：42 条的重要性分布——`0.4×3 / 0.5×3 / 0.6×4 / 0.7×22 / 0.8×9 / 0.9×1`。**52% 卡在 0.7，21% 在 0.8 以上。**

**后果**：注入排序里 importance 权重（0.35）几乎变成常数项，实际决定顺序的是新近度；`--importance 8` 和 `--importance 7` 的差别被稀释。

**做法**
- 写入口做配额提示：当天 0.7+ 已超过 N 条时提醒"今天高重要度记太多了"；
- 注入时按分位数归一（只有前 10% 吃满权重），而不是直接用原始值；
- `daily` 的 metrics 里加一条 importance 直方图，长期看漂移。

## 三、上轮遗留（仍未做）

### 5. 没有性能基准

41 条时是毫秒级，5000 条呢？`scripts/bench.py`（生成 N 条合成记忆，量 recall/remember/inject/dream 的 p50/p95）仍然没有。改 recall 阈值、改 embed 兜底，全靠手感判断"有没有变慢"。

### 6. 没有召回 ground truth

`test_niah.py` 只测"埋针能不能找回"。30 条 query→期望 id 的小集合 + `hit@3`/`MRR`，才能回答"这次改动让召回变好还是变坏"。这件事和 #1 绑在一起做最省事——反正都要把测试放回 CI。

### 7. 首次体验还是空的

`init` 之后记忆库为空，第一次 `startup` 只有"初识还没完成"。写 1 条示例记忆 + 跑一次 recall 演示（十行以内），决定新用户第一分钟要不要留下。
